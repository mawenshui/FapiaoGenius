## 2026-06-21 — 凑票架构重构：差额最小内化 + UI颜色标识

### 一、凑票架构重构：差额最小逻辑内化

#### 问题背景

原有架构中，"差额最小"同时作为金额模式（`min_diff`）和挑选策略（`closest`）存在，导致 3×5=15 种组合，且每个策略拥有独立的搜索算法，维护成本高。"差额最小"本质上应是所有模式的内在行为，而非独立选项。

#### 修改

| 文件 | 修改项 | 说明 |
|------|--------|------|
| `services/combo_service.py` | 常量字典 | 移除 `min_diff`（金额模式）和 `closest`（策略） |
| 同上 | `find_combinations()` | 删除按策略分支的 if/elif，统一调用 `_backtrack_search` |
| 同上 | `_search_closest` → `_backtrack_search` | 重命名，删除内部 `min_diff` 分支 |
| 同上 | 删除 4 个方法 | `_search_fewest`、`_search_most`、`_search_large_first`、`_search_small_first` |
| 同上 | `_greedy_search` | 删除 `min_diff` 分支 |
| 同上 | `_sort_by_strategy` | 删除 `closest` 排序分支 |
| `views/combo_page.py` | 金额模式单选按钮 | 删除"相差最小"选项 |
| 同上 | 策略单选按钮 | 删除"差额最小"选项，默认改为"张数最少" |
| 同上 | 映射字典 | 移除 min_diff 和 closest 映射 |
| `tests/` (6个文件) | 全部测试更新 | 移除 min_diff/closest 引用，54/54 测试通过 |

#### 结果

| 指标 | 修改前 | 修改后 |
|------|--------|--------|
| 金额模式 | 3 种（less/greater/min_diff） | 2 种（less/greater） |
| 挑选策略 | 5 种 | 4 种 |
| 搜索算法 | 5 个独立方法 | 1 个统一 `_backtrack_search` |
| combo_service.py 行数 | 773 行 | 387 行（-50%） |

### 二、Greater 模式剪枝缺陷修复

#### 问题背景

"可大于规定金额 + 差额最小"搜索目标 12345 元时仅找到 2 个方案（最优差额 ¥715.66），而"可少于"模式下找到 200 个方案且有差额为 0 的方案。

#### 根因

1. `greater` 模式缺少上限剪枝：`current_sum > target + threshold` 时不剪枝，搜索空间爆炸
2. 节点限制 100000 过低，因弱剪枝很快耗尽
3. 贪心策略（`large_first`/`small_first`）未区分金额模式，greater 模式返回差额为负的方案

#### 修改

| 文件 | 修改项 | 说明 |
|------|--------|------|
| `services/combo_service.py` | greater 模式剪枝 | 新增 `current_sum > target + diff_threshold → return False` |
| 同上 | greater 有效方案剪枝 | 当前和已满足条件时 `return False` 阻止继续添加 |
| 同上 | 节点限制 | 从 100000 提升至 500000 |
| 同上 | 4 处贪心验证 | `_search_large_first`/`_search_small_first`/`_greedy_search` 均改为模式感知验证 |

## 2026-06-19 — seller_name 为空时的排除法补全 + 日期多组正则修复

### 一、seller_name 为空时的排除法补全

#### 问题背景

AI 重新学习后，`餐补替票-酒店686.58.pdf` 的销售方识别为空。日志分析发现：

- 规则 `ai_learned_d9fc48a6`（六禾（大连）酒店管理有限公司）的 `seller_name` 正则为：
  ```
  91210202MA1079KY7D[\s\S]{0,50}?([\u4e00-\u9fa5（）()]{4,}(?:有限公司|...))
  ```
  即：先定位卖方信用代码 `91210202MA1079KY7D`，再在其后 50 字符内找公司名。
- 但该 PDF 的文本布局中，**信用代码出现在公司名之后**（公司名在第 469 行，信用代码在第 470 行），导致正则在信用代码之后找不到公司名。
- `buyer_name` 使用的是通用公司名模式（无信用代码锚定），匹配到了第一个公司名（买方）。
- 原有的 `seller_name==buyer_name` 纠错逻辑只在两者相等时触发，seller 为空时不触发。

#### 修改

**文件**: `parsers/pdf_parser.py`

在 `_parse_with_rules` 中新增一段：当 `seller_name` 为空但 `buyer_name` 有值时，调用 `_extract_seller_by_exclusion(text, buyer_name)` 排除法查找非买方公司名作为卖方。

### 二、日期多组正则修复

#### 问题背景

部分 AI-learned 规则的 `invoice_date` 正则生成了 3 个捕获组：
```
开票日期[：:][\s\S]*?(\d{4})年(\d{1,2})月(\d{1,2})日
```
`_try_match` 只返回 `group(1)` = "2026"（年），月/日丢失，导致开票日期只显示"2026"。

#### 修改

| 文件 | 修改项 | 说明 |
|------|--------|------|
| `parsers/pdf_parser.py` | `_try_match` | 新增多组日期检测：当有多个捕获组且第1组是4位数字（年）、第2组是1-2位数字（月/日）时，返回完整匹配（group 0），让 `normalize_date` 从中提取完整日期 |
| `builtin_rules/builtin_111_电子发票（旅客运输服务）.json` | `invoice_date` | 从 3 组改为 1 组：`(\d{4})年(\d{1,2})月(\d{1,2})日` → `([\d]{4}年[\d]{1,2}月[\d]{1,2}日)` |

## 2026-06-18（续3）— 导入阶段规则匹配、名称提取、金额提取、业务类型系统性修复

### 问题背景

清空 AI 学习规则和数据后重新导入 41 张发票，发现即使导入"通过"的发票也存在大量错误：

- **规则匹配错误**：旅馆、滴滴出行等普通增值税发票全部错误匹配到火车票规则 `builtin_111`
- **购买方/销售方名称为空**：旅馆/滴滴类发票的名称全空，因 pdfplumber 将 `购买方` 三字拆成三行
- **税额字段取错值**：`税\s*额` 正则在表头匹配后懒匹配到"数量"列而非实际税额
- **价税合计未提取**：`价税合计[（(]大写[）)]` 格式太严格
- **业务类型误判**：滴滴出行发票被标记为"铁路客运"而非"出租车/网约车"

经分析日志 `ai_fapiao_20260618_172719.log`，41 张发票中仅 6 张火车票完全正确，其余 35 张存在不同程度问题。

---

### 根因分析

| 问题 | 严重度 | 原因 |
|------|--------|------|
| 规则关键字过于宽泛 | 🔴 主因 | `builtin_111` 关键字含 `"电子发票"`（所有电子发票均匹配），评分权重平等导致旅馆/滴滴发票误用火车票规则 |
| 购买方/销售方标签被拆分 | 🔴 主因 | pdfplumber 将 `购买方` 三字按视觉列拆成 `购` → `买` → `方` 三行，正则 `购\s*买\s*方` 不跨行 |
| 税额正则匹配表头 | 🟡 次因 | `税\s*额[\s\S]*?([\d.]+)` 匹配到表头 `税率/征收率 税 额`，懒匹配取到数量字段 |
| 业务类型 `"客运"` 冲突 | 🟡 次因 | RAILWAY 和 TAXI 关键词列表都含 `"客运"`，RAILWAY 先检查导致滴滴误判 |
| 价税合计正则不灵活 | 🟡 次因 | 部分发票无大写金额行，`价税合计[（(]大写[）)]` 匹配失败 |

## 2026-06-18 — 批量AI学习自检失败问题修复 + 学习过程UI日志增强

### 问题背景

批量AI学习（`BatchLearnWorker`）的自检验证流程全部失败，每个文件5次重试后都无法通过自检。使用 `餐补替票-酒店251.15.pdf` 全流程诊断定位根因。

### 根因分析

| 问题 | 严重度 | 原因 |
|------|--------|------|
| PDF文本提取乱序 | 🔴 主因 | `pdfplumber` 默认提取将双栏发票文本搅乱，字段标签与值分离（如 `发票号码：` 和 `26112000001979557951` 相隔128字符乱码） |
| 正则不启用DOTALL | 🔴 主因 | `_parse_with_rule()` 只在 `extraction_config` 显式设置 `dotall:true` 时才跨行匹配，AI 生成的配置中默认不设此标记 |
| AI生成弱正则 | 🟡 次因 | prompt 未告知PDF文本特点，AI 生成 `\s*`（仅匹配空白符）而非 `[\s\S]*?`（跨越任意字符含换行） |
| 学习过程不可见 | 🟡 次因 | 重试的成败信息仅写入 `logger` 文件，不显示在UI「学习过程」面板中 |

---

### 修改文件

#### 1. `parsers/text_extractor.py` — 新增列拆分文本提取

**新增方法** `_extract_columns(pdf)`:

将PDF页面按 x 坐标中位数拆为 `[左栏]` / `[右栏]` 两部分，每栏内按 y 坐标分行、x 坐标排序，保留标签-值的视觉对应关系。

**修改 `extract_text()`**: 优先尝试列拆分，回退到传统提取方式。

#### 2. `services/ai_service.py` — 改进AI prompt

- 告知AI文本已按 `[左栏]`/`[右栏]` 拆分

- 示例：`发票号码[：:][\s\S]*?(\d{20})` 而非 `发票号码[：:]\s*(\d+)`
- 指出购买方在左栏、销售方和金额在右栏

  1. DOTALL 重试 → 2. `\s*` → `[\s\S]*?` 替换重试（带验证）→ 3. 智能字段回退

### 第二轮：全角括号字符类补全 + 买卖方同名回退

#### 根因

第一轮修改后仍有 2 文件失败，日志分析定位到：

1. **`_extract_company_name` 字符类遗漏全角括号**：`[\u4e00-\u9fa5]` 仅匹配 CJK 汉字（U+4E00-U+9FA5），不包含全角括号 `（）`（U+FF08/U+FF09）。含括号的公司名被截断。
2. **fallback 不触发**：当 seller_name 正则误匹配到 buyer_name 的值时，因长度 > 2 且不含银行关键词，fallback 不会触发。

#### 修改

**文件**: `views/ai_page.py`

| 修改项 | 修改前 | 修改后 |
|--------|--------|--------|
| 模式1 字符类（标准公司） | `[\u4e00-\u9fa5]{4,}` + `[\u4e00-\u9fa5]*公司` | `[\u4e00-\u9fa5（）]{4,}` + `[\u4e00-\u9fa5（）]*公司` |
| 模式2 字符类（个体工商户） | `[\u4e00-\u9fa5]{4,}个体工商户` | `[\u4e00-\u9fa5（）]{4,}个体工商户` |

| fallback 触发条件 | `not value or len(value) <= 2 or is_bank` | 新增 `or is_same_as_buyer`（seller 值等于 buyer 值时触发回退） |

## 2026-06-18（续2）— 全角括号闭合修复 + AI规则导入时seller误匹配修复

### 一、AI学习阶段：seller_name 全角括号 `）` 缺失修复

#### 问题背景

批量AI学习 `餐补替票209.pdf` 时，`seller_name` 字段 5 次重试均失败：

> 预期「高新区炙烤烧烤店（个体工商户）」, 实际提取「高新区炙烤烧烤店（个体工商户」

闭括号 `）` 被 AI 生成的正则遗漏。

#### 根因

1. AI prompt 将「个体工商户」列为公司后缀，AI 据此生成形如 `[\u4e00-\u9fa5（）]{4,}个体工商户` 的正则，只匹配到后缀文字本身，不包含紧跟的 `）`
2. `_extract_company_name` 回退函数的个体工商户模式同样缺失 `[）]?`
3. `_parse_with_rule` 中正则提取结果长度足够，不触发回退，以不完整值进入对比

#### 修改

| 文件 | 修改项 | 说明 |
|------|--------|------|
| `views/ai_page.py` | `_extract_company_name` 模式2 | 正则由 `个体工商户` → `个体工商户[）]?`，末尾补可选的闭合全角括号 |
| `views/ai_page.py` | `_parse_with_rule` 后处理 | 名称字段提取后，检测含 `（` 但缺 `）` 的情况，在原文本中查找补全 |
| `services/ai_service.py` | Prompt 增强 | `_build_learn_messages` 和 `_build_analyze_messages` 中新增 ⚠️ 提示：公司名称如「XX（个体工商户）」，闭括号 `）` 是名称的一部分，必须完整捕获 |

---

### 二、导入阶段：AI-learned规则 seller_name 误匹配为 buyer_name

#### 问题背景

AI 学习成功（4/4 规则全部保存），清空数据库重新导入 41 张发票后，**19 张发票的销售方被错误识别为 `北京正铧科技有限公司`（买方名称）**。

| 发票（示例） | 实际卖方 | 错误识别 |
|------|----------|------|
| 餐补替票-酒店686.58.pdf | 六禾（大连）酒店管理有限公司 | 北京正铧科技有限公司 |
| 餐补替票158.pdf | 景县姿含酒店 | 北京正铧科技有限公司 |
| 南京市江宁区瑞成酒店-1253.75.pdf | 南京市江宁区瑞成酒店 | 北京正铧科技有限公司 |
| ... 共 19 张 | ... | 全部错为买方名 |

#### 根因

AI 生成的 seller_name 正则统一为：

```
\d{18}[\s\S]{0,50}?([\u4e00-\u9fa5()（）]{4,}(?:有限公司|...))
```

即：找文本中**第一个** 18 位信用代码 → 附近取公司名。但在 pdfplumber 提取的发票文本中，买方的信用代码（`911101095674960279`）**总排在卖方代码之前**。因此该正则总是匹配到买方名称。

学习阶段（`BatchLearnWorker._parse_with_rule`）有 `is_same_as_buyer` 回退兜底，但导入阶段（`PDFParser._parse_with_rules`）缺少此保护。

#### 修改

**文件**: `parsers/pdf_parser.py`

| 修改项 | 说明 |
|--------|------|
| `_parse_with_rules` 新增纠错 | 对 `ai_learned_` 规则，检测 `seller_name == buyer_name` 时触发修正 |
| 策略1：通用标签回退 | 用 `销\s*售\s*方[\s\S]*?名\s*称[：:]` 标签定位正则重新提取 |
| 策略2：排除法兜底 | 新增 `_extract_seller_by_exclusion(text, buyer_name)` 方法，扫描所有公司名，排除买方和银行，返回最后一个作为卖方 |

```python
# _extract_seller_by_exclusion 核心逻辑
company_pattern = (
    r'[\u4e00-\u9fa5（）()]{4,}'
    r'(?:有限(?:责任)?公司|股份有限公司|有限责任公司'
    r'|个体工商户[）)]?'
    r'|合伙企业|经营部|服务部|分公司'
    r'|(?:酒店|宾馆|餐饮|餐厅|烧烤店|饭店|旅馆|客栈)'
    r')'
)
# 按文本位置收集 → 排除 buyer 和银行 → 返回最后一个
```
